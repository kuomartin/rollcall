# 掃描頁先回應，Apps Script 是唯一的寫入者

報到在掃描頁上用名單快取比對後立刻顯示結果，掃描放進佇列，背景每幾秒批次同步給 Apps Script；Apps Script 是唯一寫入試算表的一方，同步回應順便帶回其他入口的報到。實測 Apps Script 每次往返約 1 秒以上，沒辦法放在回應路徑上。

## Considered Options

- **入口之間用 P2P 同步（例如 Raft over WebRTC）**：其他入口看到報到的延遲能從約 3 秒降到 1 秒內，但報到允許重複，不需要共識；Raft 在入口少、手機會休眠的現場容易失去多數；WebRTC 還需要 introducer 與 TURN。不值得。
- **固定的外部 server 當 Leader**：多一套基礎設施，而且最終資料仍在主辦方的試算表裡。

## Consequences

- 離線時禁止報到：只有「最近一次同步失敗」，或「請求超過 10 秒沒回應且瀏覽器回報沒有網路」才算離線。實測 Apps Script 偶爾會有十幾秒的回應，只是慢不能鎖住入口。
- 同步協定的傳輸方式隔在一個介面後面，日後真的要 P2P 只換這一層。
