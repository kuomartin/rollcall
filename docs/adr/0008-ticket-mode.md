# 票券模式：Ed25519 簽章的序號，票種規則決定入場

每份試算表可以選票券模式。票券是 `<序號>.<sig>`，sig 是 Ed25519 對序號字串的簽章；掃描頁用 bootstrap 拿到的公鑰在本機驗章，再由「票種規則」依序號決定放行、需在名單或拒絕。這讓實體票可以批次簽發、不記名、不進試算表，與名單上的電子票用同一種 QR、同一個入口處理。

選 Ed25519：驗章端只需要公鑰，持有工作人員連結的人能驗不能簽；簽章 64 bytes，QR 密度可接受；tweetnacl 在 Apps Script 與瀏覽器跑同一份程式碼。Apps Script 沒有 CSPRNG，金鑰種子由多個 `Utilities.getUuid()` 加時間戳過 SHA-512 產生；序號是流水號，不需要亂數。

序號就是簽章涵蓋的字串，規則比對與查名單都用它。若簽章只涵蓋另一個內部 id，比對用的欄位就沒有被保護，持票人能把票改成符合較好規則的序號。流水號可行，因為安全性來自簽章，不是來自序號難猜。

前綴結尾不能是數字，任何流水號都能唯一拆回「前綴＋數字」，不同前綴永遠不會產生同一個序號。每個前綴登記用途（名單或實體），簽發名單上的序號時拒絕實體用途的前綴，所以不進試算表的實體票也不會跟名單撞號。

規則比對是從序號開頭起算的 regex，區分大小寫。序號只用 `[A-Za-z0-9_-]`，照著序號打出來的字串一定是字面比對；需要時才寫範圍或用 `$` 比對到結尾。第一條符合的規則生效，沒有符合就拒絕：簽章對了但沒有規則認得它，比較可能是設定漏了。

## Considered Options

- **用「在不在名單上」區分實體票與電子票**：電子票作廢（刪掉那一列）後會被當成實體票放行。改由規則的「需在名單」動作指定哪些序號必須在名單上。
- **亂數代號加雜湊快取，不用簽章**：每次入場都查名單時，名單本身就證明票是真的；但實體票不進名單，就只剩簽章能證明。

## Consequences

- 伺服器不驗章：持有工作人員連結本來就能報到（ADR-0002），簽章要防的是自製的假票。
- 實體票只能靠新增「拒絕」規則比對該序號或範圍來作廢；重產金鑰對會讓所有票失效。
- 放行的票在報到紀錄寫序號，不在學員名單上，所以票券模式的 bootstrap 從報到分頁讀已報到時間與入口，而不是名單的報到時間欄。
- 規則有錯時 bootstrap 不送出任何規則，掃描頁沿用先前的規則並顯示警告；只送出解析成功的部分，少了一條「拒絕」就可能錯放。
- 票券模式不支援 `lookup`：用代號或手機查詢等於繞過簽章。相機只掃 QR；輸入框保留給 USB 條碼槍，簽章無法手打。
- 寫一張 QR 儲存格圖片實測約 0.7 秒，與圖片大小無關，而選單動作單次最多執行 6 分鐘。所以實體票預設在瀏覽器畫 QR、輸出成列印頁與 CSV，伺服器只發號與簽章；名單上的簽發在時間上限前停下，再執行一次接著補 QR。
